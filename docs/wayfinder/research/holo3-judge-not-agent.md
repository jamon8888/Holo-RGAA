# Research: Holo3's actual role — text(+screenshot) judge, not GUI agent (#193)

**Date:** 2026-09-24 · **HEAD:** `0677195` (master) · **Issue:** https://github.com/jamon8888/Holo-RGAA/issues/193 (child of map #183)

External review claim: *Holo3 is only a text + screenshot judge returning a JSON verdict (`max_tokens` 512, temperature 0.1); not a GUI agent; browser tools act via CSS selectors and the accessibility tree, never pixel clicks; OSWorld/grounding strengths unexploited — so Qwen could replace it without capability loss.*

**Verdict: HOLDS-WITH-CAVEATS** (see §6). The core claim is correct; three details are off (screenshot never actually sent in production; 512/0.1 applies to only one of two completion paths; the rig loop is multi-turn text tool-calling, not single-shot).

## Per-question answers

1. **Request shape** — 512/0.1 ships, but only in `ChatTransport::complete` (transport.rs:163-164), which every `rgaa-holo` backend shares. The second production completion path (rig agent → Holo3 OpenAI-compatible endpoint) omits both fields entirely; `AgentConfig`'s 4096/0.3 are declared but never wired. Image payload is `data:image/png;base64` in an `image_url` content part — plumbed, **never used outside rgaa-holo tests**.

2. **Response handling** — fixed 3-field verdict JSON; envelope → JSON → code-block → regex extraction with retries; agent-path fallback `na`/0.0; confidence gate 0.6. No action-space format. Judge path has no `tools` field; rig path uses standard OpenAI function calling (`crawl_site` only).

3. **Browser tools** — 9 primitives, all selector/key/JS-predicate/ref based; `ClickArgs { selector: String }` is the whole click surface; Obscura guided clicks require `ax:` refs. No pixel coordinates anywhere.

4. **Rig loop** — tools = `{crawl_site}` only; browser tools not attached. Loop is multi-turn (max 3 turns) with tool-result re-entry, but **text-only — zero image re-attachment**; screenshots never reach the model on any path in production.

5. **Grounding/OSWorld** — zero surface in code; zero OSWorld mentions; the design spec explicitly rejected pixel grounding in favor of stable refs; the planned agentic "Acting" phase (act→verify loop with browser tools) was never wired into the agent.

6. **Verdict** — claim holds with caveats (below).

## Verdict: HOLDS-WITH-CAVEATS

**Holds:** Holo3 is a JSON-verdict judge, not a GUI agent; browser interaction is selector/AX-ref only, never pixel; no grounding/OSWorld capability is exercised or even representable in current traffic; Qwen (or any OpenAI-compatible chat model) could slot in without losing capability — an Ollama/Qwen alternate backend already exists officially.

**Caveats (overstatements to correct):**
1. **"text+screenshot judge" understates it:** in the shipped pipeline it is a **text-only** judge — `evaluate_multimodal` has no production caller; the pipeline feeds a DOM-census `PageContext`, never a screenshot.
2. **"max_tokens 512 / temp 0.1" is path-specific:** true for `rgaa-holo`'s transport; the rig-agent path (which performs the actual IA-assistée evaluations in `pipeline.rs`) sends neither param, and the config values that would apply (4096/0.3) are dead.
3. **Not single-shot:** the rig loop is multi-turn tool-calling (≤3 turns) against the same Holo3 endpoint — but text-only (`crawl_site`), so still no GUI/visual agent loop.
4. **"Unexploited" is right, but nuance:** the selector/AX-ref tool surface *was built* (9 tools) and the spec deliberately rejected pixel grounding — the gap is that these tools were never registered on the agent, not that the wrong kind of tool was built.
